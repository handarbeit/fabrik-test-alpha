## Background

This is a live end-to-end regression scenario for Fabrik's cross-repo decomposition. The work needs changes in two repositories (`handarbeit/fabrik-test-alpha`, this repo, and `handarbeit/fabrik-test-beta`), and the alpha change depends on a function that must first exist in beta. The pipeline is therefore expected to decompose the work: Plan spawns a child issue targeting the beta repo, and the alpha work waits until the child has landed.

The scenario guards two earlier fixes:
- **#803**: on-demand initialisation of a spawn-target repository.
- **#1308**: a per-run-unique fixture token, so a run can only pass on its own output and not on leftovers from an earlier run.

The scenario's final assertion checks that the exact function name and string literal below appear in the beta repo. They carry the per-run-unique token (`20261021-193526-5800`) and must be used verbatim, never replaced or "improved".

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Beta repo gains the greeting function via a spawned child (Priority: P1)

The pipeline decomposes the work and delivers the beta-side change through a child issue targeting `handarbeit/fabrik-test-beta`.

**Why this priority**: This is the behaviour under test. The final assertion checks that this text lands in beta, and alpha cannot be completed without it.

**Independent Test**: Inspect the beta repo's default branch after the run for the function, its test, and the expected return literal.

**Acceptance Scenarios**:

1. **Given** this issue reaches Plan, **When** Plan decomposes the work, **Then** it emits a `FABRIK_SPAWN_CHILD_BEGIN` block targeting `handarbeit/fabrik-test-beta` that describes the beta-side change.
2. **Given** the child issue is implemented and merged in beta, **When** `pkg/greeting/greeting.go` is inspected, **Then** it contains an exported function `HelloE2E202610211935265800() string` returning exactly `"e2e-cross-repo-spawn-20261021-193526-5800"`.
3. **Given** the same merge, **When** `pkg/greeting/greeting_test.go` is inspected, **Then** it contains a test that exercises `HelloE2E202610211935265800` and passes.

---

### User Story 2 - Alpha consumes the new function after beta lands (Priority: P1)

Once the beta change has landed, this repo's `main.go` calls the new function and prints its result.

**Why this priority**: It completes the cross-repo flow and proves the ordering constraint (beta before alpha) held.

**Independent Test**: Build and run alpha after beta's change is available; the output includes the literal string.

**Acceptance Scenarios**:

1. **Given** the beta function exists and is reachable as a dependency, **When** alpha's `main.go` is run, **Then** it prints `e2e-cross-repo-spawn-20261021-193526-5800` in addition to its existing output.
2. **Given** the beta change has not yet landed, **When** alpha's implementation is attempted, **Then** alpha does not land code that imports the missing function (it waits on the child via the parent's `blockedBy` link).
3. **Given** the module graph changed, **When** the build is checked, **Then** `go mod tidy` has been run if needed and the build succeeds.

---

### Edge Cases

- The beta repo may not yet be initialised for spawning (the #803 case): on-demand initialisation must still allow the child to be created and worked.
- The function name or literal must not be altered, abbreviated or regenerated by any stage; any deviation fails the final assertion.
- Alpha's existing `main.go` behaviour must be preserved; the new call is additive.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Plan MUST decompose the work by emitting a `FABRIK_SPAWN_CHILD_BEGIN` block targeting `handarbeit/fabrik-test-beta` for the beta-side change.
- **FR-002**: The beta change MUST add an exported function `HelloE2E202610211935265800() string` to `pkg/greeting/greeting.go` that returns exactly `"e2e-cross-repo-spawn-20261021-193526-5800"`.
- **FR-003**: The beta change MUST add a test for that function to `pkg/greeting/greeting_test.go`.
- **FR-004**: The alpha change MUST update `main.go` to call `greeting.HelloE2E202610211935265800()` and print the result, keeping all existing behaviour.
- **FR-005**: The alpha change MUST run `go mod tidy` where needed so the module builds.
- **FR-006**: The beta change MUST land before the alpha change; alpha MUST NOT land code that depends on a function not yet present in beta.
- **FR-007**: The function name and string literal MUST be used verbatim in every stage and artifact, with no substitution of other names or tokens.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: After the run, the beta repo's default branch contains `HelloE2E202610211935265800` returning `"e2e-cross-repo-spawn-20261021-193526-5800"`, with a passing test.
- **SC-002**: Running alpha after the run prints `e2e-cross-repo-spawn-20261021-193526-5800`.
- **SC-003**: A child issue exists in `handarbeit/fabrik-test-beta` created by Plan's spawn, and this issue is blocked by it until it completes.
- **SC-004**: The scenario's final assertion (the exact token text present in the beta repo) passes.

## Assumptions

- The beta repo already has a `pkg/greeting` package with `greeting.go` and `greeting_test.go`, as the issue implies.
- Alpha already depends on the beta module's `pkg/greeting` package or can add the dependency via `go mod tidy`.
- The `fabrik:yolo` label means stages auto-advance and the child is handled by the normal pipeline.
- The token `20261021-193526-5800` is final and per-run-unique; it is not regenerated.

## Out of Scope *(optional)*

- Changes to Fabrik engine behaviour; this issue only exercises it.
- Changes to the beta repo beyond the function and its test.
- Other greeting functions, refactors, or documentation changes in either repo.
- Further e2e scenarios or fixture-token mechanics.
